# План мультиплеера — LessonGame

Статус: **M0–M5 выполнены** — кооп до 20 игроков на listen-server работает, мир живёт на сервере, поздний вход и выходы обработаны, трафик измерен. Следующий этап — **M6 «Выделенный сервер»**, спланирован ниже и ещё не начат. Целевая версия движка — Godot 4.6 (GDScript).
Общение — по-русски, код и имена — по-английски (см. `AGENTS.md`).

Версия движка — **4.6**, и это осознанно: переход на 4.7 рассмотрен (последняя стабильная на тот момент — 4.7.2) и отложен, потому что для M6 он ничего не добавляет (ломающих изменений и нововведений по мультиплееру в 4.7 нет), а трогать рабочую версию ради редакторских удобств смысла нет. Возвращаться к вопросу — только при реальной нужде.

## 0. Кратко: что это, на чём стоим, куда идём

Раздел для того, кто открыл документ впервые (в том числе для новой сессии агента). Дальше — детали, история решений и этапы.

**Игра.** 2D-песочница на Godot 4.6 (GDScript): персонаж ходит по карте, рубит деревья и камни, собирает и использует предметы, открывает двери, охотится на животных. До этого плана игра была одиночной: точки входа в `core/`, игровая логика в `shared/`.

**Что делаем.** Кооператив PvE до 20 игроков по схеме **listen-server**: один игрок создаёт игру и играет сам, остальные подключаются по IP или через поиск в локальной сети. Транспорт — ENet (UDP), фиксированный порт 8910. Клиенты друг с другом не соединяются: весь трафик идёт через хоста (`server_relay = true`).

**Принципы, действующие во всём коде.** Их достаточно понимать, чтобы читать любую мультиплеерную правку:

1. **Мир считает сервер.** Хост — источник истины по урону, смерти объектов и мобов, луту, подбору предметов, дверям и по тому, что уже сломано. Клиент присылает намерение, сервер валидирует и рассылает результат. В одиночной игре сервером считается сам игрок, отдельной ветки логики нет (`WorldSync.is_server()`).
2. **Своим движением владеет клиент.** Владелец двигает персонажа и пишет позицию в `NetTarget` внутри `player.tscn`, остальные получают её через `MultiplayerSynchronizer` и плавно доезжают. Модель клиент-авторитетная: сервер позицию не проверяет — это осознанно и меняется только в M6.4.
3. **Каждое игровое событие адресовано игроку.** Сигналы `PLA_*`, `INV_*`, `EQU_*` первым аргументом несут владельца; подписчик обязан сравнить его со своим игроком (`MatchState.local_player` или `MatchState.find_owner_player(self)`). Иначе событие одного игрока сработает у всех.
4. **Спавн детерминированный.** Игроки создаются на всех пирах из `MatchState.participants` в одном и том же порядке, а не рассылкой по сети: по путям узлов адресуются удаление и снапшот, поэтому пути обязаны совпадать. Лут, наоборот, спавнит сервер и рассылает копии с детерминированными именами (`Item_<id>`).
5. **Сеть — отдельный слой.** Единственные места, где вообще упоминается сеть: автолоады `NetworkManager` (транспорт, рукопожатие, пароль, LAN-поиск) и `WorldSync` (авторитет над миром, состояние мира, снапшот) плюс `MultiplayerSynchronizer` в `player.tscn`. Остальные системы общаются через шину `EventSystem` и о подключении не знают.
6. **Всё видимое приходит по сети явно.** Движение — синхронизатор; экипировка, сторона взгляда и анимация использования — RPC от владельца. Если что-то не рассылается, чужие игроки этого не увидят: так было с оружием в руках, пока это не починили.

**Что уже работает (M0–M5):**

| Этап | Итог |
|---|---|
| M0 | игровые события адресованы игроку, одиночная игра не сломана |
| M1 | ENet-транспорт, лобби, пароль, поиск в локальной сети |
| M2 | игроки в мире: детерминированный спавн, репликация движения |
| M3 | ники и цвета над персонажем, список игроков с пингом |
| M4 | авторитет мира (урон, смерть, лут, подбор, двери) и снапшот для позднего входа |
| M5 | видимость по расстоянию, выход игрока и хоста, стресс на 20 игроков |
| сверх плана | экипировка, сторона взгляда и анимация использования тоже репликуются |
| фикс после M5 | репликация движения у позднего входа: новичок не получал движение уже игравших (и его самого при этом видели все) — см. §2 и §10 |

**Чего нет:** пули не репликуются (в игре они не используются), запасы здоровья и маны чужих игроков не передаются (они нигде не показываются), серверной проверки движения нет.

**Что дальше:** этап **M6 «Выделенный сервер»** (§5) — сервер без локального игрока, обвязка и эксплуатация, шифрование и аутентификация, серверная симуляция движения. Пока только план, кода нет.

## 1. Рамки

| Параметр | Решение |
|---|---|
| Режим | Кооп в общем мире, PvE |
| Топология | Listen-server: один из игроков — хост, у него авторитет по миру |
| Транспорт | ENet (UDP), релей трафика через сервер (`multiplayer.server_relay = true`) |
| Игроков | до **20** всего (хост + до 19 клиентов) |
| Подключение | ввод IP вручную **и** LAN-браузер (автопоиск хостов) |
| Порт | фиксированный — **8910**, в UI не настраивается |
| Пароль на вход | **опционально**: хост может задать пароль, пусто — вход свободный |
| Поздний вход (late join) | нужен: подключение к идущей игре с ресинком мира |
| Имена и цвета игроков | нужны: ник и цвет отображаются над персонажем |
| Чат | **не делаем** — отдельная фича на будущее (закладываем место, но не реализуем) |
| Точка спавна | пока одна общая на всех (пересмотреть при 20 игроках) |
| Одиночная игра | остаётся **отдельным пунктом** меню, отдельной ветки «мультиплеерной» логики для неё не делаем |
| Первая веха | техдемо: двое игроков бегают и видят друг друга |

## 2. Архитектура

```
                 ┌──────────────────────────────┐
                 │ Хост (listen-server)         │
                 │  авторитет по миру           │
                 │  мобы, лут, урон, двери,     │
                 │  спавн, состояние мира       │
                 └───────┬──────────────┬───────┘
                 ENet    │              │   ENet
        ┌────────────────┘              └────────────────┐
        │                                                 │
   ┌────▼─────┐                                      ┌────▼─────┐
   │ Клиент 1 │  … до 19 клиентов …                  │ Клиент N │
   │ свой ввод│  ввод и камера — только своё          │          │
   └──────────┘                                      └──────────┘
```

- **Сервер владеет:** уроном, смертью мобов и объектов, спавном лута, подбором предметов, состоянием дверей и состоянием мира (что сломано и подобрано) — реализовано в автолоаде `WorldSync`.
- **Клиент владеет:** своим вводом, камерой, курсором и собственным движением — позицию не проверяет даже сервер (§0, принцип 2).
- **Репликация движения — как сделано:** `MultiplayerSynchronizer` на дочернем узле `NetTarget` внутри `player.tscn`, синхронизируется только `position`, интервал 1/20 с; наблюдатели плавно доезжают (`REMOTE_SMOOTH_SPEED = 15`), при расхождении больше 300 px переносятся мгновенно. Своё движение уходит только пирам, уже вошедшим в мир: видимость синхронизатора включается адресно (`set_visibility_public(false)` + `set_visibility_for` в `_apply_visibility`). Это обязательное условие работы, а не оптимизация — подробности в §10. Радиус интереса 1500 px в коде есть, но выключен (`INTEREST_RADIUS_ENABLED = false`).
- **Действия:** ручные `rpc`/`rpc_id` — намерение уходит на сервер, сервер рассылает результат (удар, подбор, дверь, смерть, спавн лута).
- **Спавн объектов — как сделано:** от `MultiplayerSpawner` отказались. Игроки создаются детерминированно из `MatchState.participants`, а лут создаёт сервер в `ManagerSpawner` и рассылает копии с именем `Item_<id>`, чтобы пути совпадали на всех пирах.
- **Пули:** в игре пока не используются (`Player.shoot()` никто не вызывает) и потому не репликуются. Если понадобятся — по плану попадания считает сервер, а клиентские пули остаются визуалом (§7).

### Проверенные API Godot 4.6

Наличие проверено движком (`--headless --script`, ClassDB): `ENetMultiplayerPeer.create_server/create_client/set_bind_ip`, `MultiplayerSpawner` (`spawn_function`, `spawn_path`, `spawn_limit`, `add_spawnable_scene`, `spawn`), `MultiplayerSynchronizer` (`replication_interval`, `replication_config`, `public_visibility`, `root_path`, `set_visibility_for`, `set_visibility_public`, `update_visibility`), `SceneMultiplayer` (`set_auth_callback`, `set_root_path`, `server_relay`, `allow_object_decoding`), `Node.set_multiplayer_authority/is_multiplayer_authority/rpc_config/rpc_id`, `SceneTree.get_multiplayer/set_multiplayer`, `ProjectSettings` — `physics/common/physics_interpolation`.

Важно: **`MultiplayerSynchronizer.add_property()` не существует** — список свойств задаётся через `replication_config` (`SceneReplicationConfig`), то есть в инспекторе. Список пиров берётся из `multiplayer.get_peers()` (метод `MultiplayerAPI`, не `SceneMultiplayer`).

## 3. Что блокировало в текущем коде (историческая справка: состояние до M0)

Всё перечисленное исправлено в M0, раздел оставлен, чтобы было видно, откуда взялись решения §4. Это не список текущих проблем.

**№1 — глобальный `EventSystem` без адресата (главный блокер).** Сигналы `PLA_*`, `INV_*`, `EQU_*` (`core/global_events/event_system.gd`) слушают подписчики **всех** игроков:

- `shared/actors/player/managers/player_stats_manager/player_stats_manager.gd` — `PLA_change_energy` от одного игрока уменьшит энергию всем;
- `shared/gui/components/player_menu/managers/manager_inventory/manager_inventory.gd` — `INV_try_to_pickup_item` подберёт предмет каждому;
- `shared/actors/player/equippable_item_holder/equippable_item_holder.gd` — `EQU_equip_item` экипирует оружие всем;
- `shared/gui/components/player_stats/player_stats.gd` — HUD получает статы всех игроков подряд.

**№2 — ввод читается напрямую.** `shared/actors/player/player.gd` (`Input` в `_physics_process`, `_unhandled_key_input`), `shared/objects/door/door.gd` (`_input`, KEY_E/KEY_W), `shared/objects/items/components/items/base_item/pickuppable_item.gd` (`_input`, 'active'). Плюс проверки `body is Player`, реагирующие на **любого** игрока, а не на локального.

**№3 — камера и курсор.** `Camera2D` внутри `Player` (`shared/actors/player/player.tscn`) — активной должна быть только локальная. `CursorGame` и `get_global_mouse_position()` локальны по смыслу; на сервере направление выстрела берётся из RPC.

**№4 — мир управляется локально.** `HittableObjectTemplate.die()`, `AnimalTemplate.set_state(Dead)`, `ManagerSpawner.on_spawn_scene`, `EquippableWeaponeTemplate.check_hit()` выполняются в том процессе, где нажали.

**№5 — мелочи с последствиями.** Отладочный `Line2D` в `check_hit()` уедет в сетевую игру; `Bullet` — `RigidBody2D`, плодящий дочерние пули по коллизии (недетерминированная физика); статичный узел `Player` в `core/stages/levels/level_1.tscn`.

## 4. Проектные решения (приняты до начала работ, в основном реализованы как задумано)

1. **Авторитет.** Сервер решает всё, что меняет общий мир. Клиент присылает намерение («выстрелил в эту точку», «подобрать этот предмет»), сервер валидирует (дистанция, кулдаун, живость объекта) и рассылает результат.
2. **Развязка шины событий.** `EventSystem` остаётся для UI/системных сигналов (`UI_*`, `BUL_*`, `SPA_spawn_scene`); игровые `PLA_*` / `INV_*` / `EQU_*` получают первым аргументом владельца (`player: Player` или `peer_id`), подписчики фильтруют `if owner != local_player: return`. Альтернатива — локальная шина-ребёнок `Player` — чище, но инвазивнее; начинаем с первого варианта, потому что он диффится постепенно и не ломает одиночную игру.
3. **Репликация движения** — `MultiplayerSynchronizer`; при необходимости позже снапшот-буфер с интерполяцией и `physics/common/physics_interpolation`.
4. **Поздний вход** — сервер по `peer_connected` присылает снапшот мира: список уже уничтоженных объектов и подобранных предметов. Источник истины — `MatchState` и состояние в `WorldSync` (словари «путь узла → состояние»), а не сами узлы сцены.
5. **LAN-поиск** — `PacketPeerUDP` с `set_broadcast_enabled(true)`: хост раз в секунду шлёт бродкаст-бекон `{name, port, players, max, has_password}` на фиксированный порт, клиенты слушают и собирают список; ручной ввод IP остаётся как запасной путь (и на случай, когда бродкаст режется фаерволом).
6. **Имена и цвета игроков** — часть `MatchState`: `peer_id → {name, color}`; ник и цвет над персонажем — в составе `player.tscn`.
7. **Одиночная игра** — не отдельная кодовая ветка: тот же `PlayerSpawner` создаёт одного локального игрока без сети (`multiplayer.multiplayer_peer == null`).
8. **Порт** — фиксированный `8910`: `const DEFAULT_PORT := 8910` в `NetworkManager`, поля порта в UI нет. Если порт занят — понятная ошибка при попытке хостить, а не молчаливый отказ.
9. **Пароль (опциональная функция).** Хост может задать пароль в лобби; пустое поле — вход свободный. Реализация — рукопожатие после установления соединения: клиент сразу после `connected_to_server` отправляет `rpc_id(1, ...)` с паролем, сервер сравнивает и при несовпадении отключает пира (`multiplayer.multiplayer_peer.disconnect_peer(id)`) с сообщением. **До успешной проверки игрок не спавнится и не переводится на карту** — иначе пароль обходится сторонним клиентом. Пароль защищает от случайных подключений, но не от перехвата: канал не шифруем, шифрование (DTLS в ENet) — отдельная задача с проверкой API.

## 5. Этапы

Размеры: S — мало, M — средне, L — много.

### M0. Развязка игроков от глобальной шины (без сети) — **L** — сделано

- Автолоад `MatchState` (`core/global_match/match_state.gd`): `local_player`, `players[peer_id]`, `is_host`, `max_players = 20`; свободный `peer_id`, если игрок пришёл без сети; `find_owner_player()` — владелец-игрок для узла.
- Игровые сигналы `PLA_*`/`INV_*`/`EQU_*` первым аргументом несут игрока-владельца: эмиттеры UI берут `MatchState.local_player`, подписчики фильтруют (менеджеры игрока — по своему игроку, UI — через `MatchState.is_local_event()`).
- `body is Player` → сравнение с `MatchState.local_player` в `pickuppable_item.gd` и `door.gd`.
- `Player`: физика и `_unhandled_key_input` — только для локального игрока; `camera.enabled` только у локального.
- HUD (`player_stats.gd`, `hot_bar.gd`) и меню игрока реагируют только на локального игрока.

Подводные камни, найденные на M0:

- Движок подставляет `OfflineMultiplayerPeer` (unique_id = 1), когда сети нет: «офлайн» — это `peer == null` **или** `peer is OfflineMultiplayerPeer`, иначе единственный игрок не становится локальным.
- `bullet.gd` держал `preload` собственной сцены `bullet.tscn`, а сцена ссылается на скрипт — цикл «скрипт ↔ сцена», ресурсы не освобождались при выходе. Как только `Player` стал загружаться на старте (ссылка из автолоада), гейт `--headless --quit` начал печатать `ERROR: ... leaked at exit`; исправлено ленивой загрузкой сцены по пути.

**Готово, когда:** одиночная игра играется ровно как раньше, `--headless --path . --quit` без ошибок — **выполнено** (см. §8).

### M1. Транспорт, лобби, LAN-поиск, пароль — **M** — сделано

- Автолоад `NetworkManager` (`core/global_network/network_manager.gd`): ENet на фиксированном `DEFAULT_PORT = 8910`, `max_clients = 19`, `host_game()/join_game()/disconnect_game()` с понятными ошибками (в том числе «Порт 8910 уже занят»), сигналы `server_started/server_stopped/participant_joined/participant_left/connection_succeeded/connection_failed/server_disconnected/join_rejected`.
- Рукопожатие: клиент после подключения шлёт имя и пароль, хост проверяет пароль и лимит мест и только затем добавляет участника в `MatchState.participants` и рассылает состав. При отказе хост сначала отправляет причину и лишь через `REJECT_GRACE = 0.4` с отключает пира; разрыв до конца рукопожатия клиент трактует как отказ, а не как уход хоста.
- Лобби `shared/gui/components/navigations/navigation_multiplayer/`: имя, адрес, пароль (опционально), «Создать игру» / «Присоединиться», список игроков, список найденных игр, статус, «Назад»; `ESC` → `EventSystem.UI_last`.
- `UIConfig.Keys.MenuMultiplayer = 5` + путь; кнопка «Мультиплеер» → `UI_replace`.
- `LanDiscovery` (`core/global_network/lan_discovery.gd`): хост раз в секунду шлёт бекон на порт 8911 (отдельный от игрового, иначе конфликт с ENet на одной машине), клиент собирает список с именем, числом игроков, лимитом и пометкой «с паролем»; записи старше 3,5 с отбрасываются.

Подводные камни, найденные на M1:

- Новый `class_name` не виден движку, пока проект не переимпортирован: без `--headless --import` автолоад падает с `Could not find type "LanDiscovery"`.
- `PacketPeerUDP.set_broadcast_enabled()` возвращает `void`, а не `Error` — проверять результат нельзя.
- Сервер, отключающий пира сразу после RPC с причиной отказа, теряет эту причину: клиент видит только разрыв. Отсюда `REJECT_GRACE` и трактовка раннего разрыва как отказа.
- Смоук-раннер обязан иметь жёсткий таймаут выхода: при ошибке в `_ready()` процесс Godot иначе висит вечно.
- **На одной машине слушатель поиска может быть только один** (порт 8911, у `PacketPeerUDP` нет разделения порта): второе окно игры не могло встать на прослушивание, молча сдавалось и до конца сессии показывало пустой список найденных игр — хотя хост рядом исправно вещал. Теперь занятый порт не приговор: пока лобби открыто, попытки повторяются каждые 2 с, а в заголовке списка видно «поиск недоступен» или «вы хост».

**Готово, когда:** два запуска игры соединяются и по IP, и через LAN-браузер; список игроков обновляется; свободный хост пускает без пароля, хост с паролем пускает только с верным паролем; отказ соединения показывает внятное сообщение, а не зависание — **выполнено** (см. §8).

### M2. Техдемо: игроки в мире (первая веха) — **M** — сделано

- Хост начинает игру из лобби (кнопка «Начать игру» видна только хосту), `NetworkManager.start_game()` рассылает RPC и меняет сцену у всех пиров синхронно.
- Статичный `Player` из `level_1.tscn` убран; в `map_1.tscn` появились `Players` + `PlayerSpawner` (`core/stages/managers/player_spawner/`). Точка появления — маркер `SpawnPlayer` в группе `player_spawn`, сдвиг 70 px по индексу (иначе игроки стоят друг в друге и демо выглядит как один игрок).
- Игроки создаются детерминированно на всех пирах из `MatchState.participants` (отступление от `MultiplayerSpawner`: при смене сцены пиры оказываются в ней в разные кадры, и реплицированный спавн может прийти раньше, чем у клиента появится сцена). Авторитет отдаётся владельцу через `set_multiplayer_authority(peer_id)`.
- Движение: `NetTarget` (Node2D) + `MultiplayerSynchronizer` внутри `player.tscn`, свойство `position`, интервал 1/20 с. Локальный игрок пишет туда свою позицию, наблюдатели плавно (`REMOTE_SMOOTH_SPEED = 15`) едут за целью, при скачке больше 300 px — мгновенный перенос (телепорт двери, падение в пропасть).
- Чужой игрок не крутит физику и ввод, его камера выключена; HUD и меню по-прежнему привязаны к локальному игроку.
- Экипировка и сторона взгляда репликуются (`EquippableItemHolder`): владелец применяет предмет у себя и рассылает `_remote_equip`/`_remote_unequip`/`_remote_flip`, остальные видят то же оружие в тех же руках. Доделано после баг-репорта «выбор оружия не виден другому игроку» — изначально в M2 реплицировалось только движение.
- Использование предмета тоже видно: владелец рассылает `_remote_use`, когда анимация действительно началась (а не каждый кадр удержания кнопки), остальные проигрывают ту же анимацию. Эффекты — урон, лечение, удаление расходника — применяет только владелец: их вызывают дорожки анимации, поэтому каждая эффектная функция проверяет `is_owner_local()`. Без этого чужая копия оружия отправляла бы на сервер второй удар, а расходник лечил бы дважды.
- Зачаток позднего входа: если игрок подключился, когда игра уже идёт, хост сразу отправляет его на карту (флаг `_game_started` + `_load_game_scene` в рукопожатии). Полный ресинк состояния мира (что уже сломано и подобрано) остаётся на M4.

Подводные камни, найденные на M2:

- `add_child()` внутри `_ready()` падает с `Parent node is busy setting up children`, если сцена в этот момент достраивается — а это ровно случай смены сцены. Спавн игроков и создание пробы в смоуке сделаны отложенными (`call_deferred`).
- Формат `SceneReplicationConfig` пришлось получить эмпирически: `properties/0/path = NodePath(":position")`, `properties/0/spawn = true`, `properties/0/replication_mode = 1`.
- Дочерний узел-цель обязателен: если синхронизировать `position` самого тела, у наблюдателей позиция прыгает с частотой сети (20 Гц).

**Готово, когда:** два окна на localhost видят оба тела, движение плавное, ничего не дёргается и не двоится; headless-прогон «хост + клиент» пишет в лог установленное соединение — **выполнено** (см. §8). Проверено headless-тестом: оба пира видят двух игроков, локальный игрок и его камера — только свои, движение хоста доходит до клиента.

### M3. Имена, цвета и список игроков — **S** — сделано

- Ник и цвет над персонажем: `Label` в `player.tscn`, у локального игрока скрыт (своя табличка перед глазами мешает), у чужих — с обводкой и цветом игрока.
- Цвет не передаётся по сети: `MatchState.participant_color(peer_id)` выводит оттенок из `peer_id` (золотое сечение по hue), поэтому он одинаков у всех пиров без синхронизации.
- Список игроков — переиспользуемый узел `PlayerRoster` (`shared/gui/components/player_roster/`): ник, цвет, пинг, пометки «вы»/«хост». Стоит в лобби и в игровом меню, сам обновляется при смене состава и раз в секунду ради пинга; в одиночной игре игровое меню его прячет.
- Пинг берётся из `ENetPacketPeer.get_statistic(PEER_ROUND_TRIP_TIME)`. При релее через сервер клиент видит напрямую только хост, поэтому у остальных «—» — это ожидаемо, а не ошибка.
- Лимит мест: ENet не пускает сверх `max_clients = 19`, плюс проверка в рукопожатии; сообщение об отказе дополнено («хост недоступен или нет свободных мест»).

**Готово, когда:** ники и цвета видны и совпадают у всех, цвета различимы, 21-й игрок получает отказ и не ломает сессию — **выполнено** (см. §8). Цвет хоста, посчитанный на хосте и полученный клиентом в табличке, совпадает (`4078ff`).

### M4. Авторитет мира и поздний вход — **L** — сделано

- Автолоад `WorldSync` (`core/global_world/`): считает, кто сервер, применяет удары, рассылает уничтожение и спавн, решает споры за предмет и хранит состояние мира.
- Удары: анимация оружия как и раньше вызывает `check_hit()`, но теперь это только намерение — клиент отправляет луч на сервер, сервер сам делает `intersect_ray` и применяет урон (`WeaponItemResource` берётся из `ItemConfig` по ключу предмета, начало луча проверяется по расстоянию до стрелка). Отладочный `Line2D` убран из игры под флаг `WorldSync.DEBUG_RAY`.
- Смерть дерева/камня: `die()` выполняется только на сервере — он спавнит лут и рассылает `_apply_death`; клиенты просто убирают копию (`apply_remote_death`). Повторные удары в том же кадре больше не сыпят лут дважды.
- Мобы: урон применяет сервер, `set_state(Dead)` на сервере спавнит мясо и рассылает смерть; клиенты проигрывают ту же смерть без спавна.
- Лут: `ManagerSpawner` создаёт предмет только на сервере, имя узла детерминировано (`Item_<id>`), остальные получают копию по RPC — поэтому путь совпадает и предмет можно убрать у всех.
- Подбор: `ManagerInventory` проверяет место в рюкзаке и просит сервер; сервер отдаёт предмет первому (`_request_pickup`), помечает путь уничтоженным, убирает его у всех и присылает предмет только победителю.
- Двери: состояние `_is_open` рассылается всем при переключении (телепорт по-прежнему двигает только своего игрока). Серверной арбитрации тут нет — читерской поверхности в этом нет, а расхождение картинки было бы заметно.
- Снапшот мира: клиент, попав на карту, просит состояние (что сломано и что заспавнено) и применяет его — поздний вход видит сломанное дерево сломанным и подобранный лут отсутствующим.
- Осознанные упрощения: инвентарь остаётся у владельца (сервер не ведёт его копию — для кооператива это не нужно, полный зеркальный инвентарь уезжает в M5), пули не репликуются (в игре они пока не используются: `Player.shoot()` никем не вызывается).

**Готово, когда:** двое рубят одно дерево — лут достаётся одному; моб умирает один раз; предмет не дублируется; подключившийся позже видит уже сломанное дерево сломанным — **выполнено** (см. §8). Проверено headless-тестом: лут (3 предмета) появился у обоих, гонку за предмет выиграл ровно один, поздний вход получил сломанное дерево и лут из снапшота.

### M5. Масштаб до 20 игроков и устойчивость — **L** — сделано

- Interest management: локальный игрок сам решает, кому слать своё движение. Скрыто всё, что дальше `VISIBILITY_RADIUS = 1500` px (гистерезис 250 px, чтобы не мигало на границе), и все пиры, которые ещё не на карте (`WorldSync.is_peer_in_world`). Сервер видит всех всегда — он проверяет удары. `MultiplayerSynchronizer.set_visibility_for()` + `update_visibility()`, пересчёт раз в 0,5 с и сразу по `peer_connected`/`participants_changed`.
- Побочный, но важный эффект: движение больше не рассылается тем, кто ещё в лобби — раньше при позднем входе лог забивался `Node not found: "…/NetTarget/MultiplayerSynchronizer"` (до 188 строк за прогон), теперь чисто.
- Троттлинг: синхронизируется только `position`, интервал 1/20 с (с M2), `MultiplayerSpawner` не используется — лут спавнит сервер с детерминированными именами.
- Выход игрока: `participants_changed` → `PlayerSpawner` убирает узел; проверено стрессом (счётчик игроков у остальных убывал по мере выхода ботов).
- Выход хоста: клиент ловит `server_disconnected`, выходит из игры и возвращается в меню (`scene=menu.tscn`), причина показывается в лобби через `NetworkManager.last_notice`.

Стресс-прогон (19 ботов + хост = 20 игроков, всё на одной машине, местная сеть):

| Метрика | Значение |
|---|---|
| Боты | 19 из 19 подключились, `players=20`, все вышли штатно |
| Отправка хоста | ~2,8 МБ за сессию ≈ **70 КБ/с** (~0,56 Мбит/с) на 20 игроков |
| Приём хоста | ~2,9 МБ ≈ 74 КБ/с |
| На одного клиента | ~0,5 КБ/с на каждого видимого игрока (≈30 байт на снапшот при 20 Гц) |
| Тот же тест до AOI | ~3,2 МБ ≈ 80 КБ/с |

Вывод: оценка из §6 (≈1,9 Мбит/с) оказалась пессимистичной — на практике ~0,6 Мбит/с, а AOI дополнительно срезает рассылку далёким и ещё не вошедшим в мир.

Не сделано: проверка на искусственном лаге — у ENet в Godot нет встроенной эмуляции задержки, для честного теста нужен внешний инструмент (Clumsy на Windows, `tc netem` на Linux). Записано в §9.

**Готово, когда:** 20 headless-клиентов держат сессию стабильно, трафик хоста укладывается в бюджет (см. §6), отключение любого участника не ломает игру — **выполнено** (см. §8).

### M6. Выделенный сервер — **L** — запланирован, не начат

Смысл: игра крутится на машине, за которой никто не играет, а все — включая «хозяина» — подключаются клиентами. У listen-server есть врождённая цена: уход хоста убивает сессию (см. §7), у хоста преимущество по задержке, и его компьютер определяет качество игры для всех.

Почему этап дешевле, чем выглядит: мир у нас уже серверный (урон, смерть, лут, подбор, снапшот — M4), везде принято «пир 1 — это сервер» (`WorldSync.is_peer_in_world(1)`, проверка удара, RPC к единице), игроки спавнятся детерминированно из `MatchState.participants`. То есть выделенный сервер — это в основном «пир, который не играет за игрока».

#### M6.1 Минимальный рабочий режим — **M**

- `NetworkManager.Mode.DEDICATED` + флаг запуска (`--server`): разбор аргументов как в смоуке (`OS.get_cmdline_args`).
- Сервер не грузит лобби и HUD: прикрыть места, где интерфейс трогает `MatchState.local_player == null`; в списке игроков сервер помечать «сервер», а не «хост».
- Матч стартует сам: автозапуск при наборе игроков либо по админ-команде (сейчас игру начинает кнопка хоста).
- `is_server()` должен считать сервером и этот режим (сейчас это «не подключён или хостит»).
- Проверка: `--server` + боты из существующего смоука (19 ботов = 20 игроков), плюс проверки M4/M5 против сервера, а не против хоста-игрока.

#### M6.2 Обвязка и эксплуатация — **M**

- Конфиг: порт (8910/UDP), лимит игроков (20), карта, пароль или токен, имя сервера.
- Админ-команды: кик, старт/стоп, смена карты — RPC от админа или консоль.
- Как игроки находят сервер: прямой IP работает уже сейчас, LAN-поиск (8911) остаётся только для локальной сети; для интернета нужен список серверов или внешний сервис.
- Развёртывание: headless-экспорт (Linux), systemd или docker, открытый UDP-порт, читаемые логи. В пресете экспорта завести свой тег (например, `server`) и проверять `OS.has_feature("server")` — в редакторе `dedicated_server` не выставлен (проверено в 4.6).
- Запас по надёжности: `create_server(port, max_clients, max_channels, in_bandwidth, out_bandwidth)` с явными лимитами.

#### M6.3 Защита канала и аутентификация — **M**

- DTLS: в 4.6 у `ENetConnection` есть `dtls_server_setup` / `dtls_client_setup` (найдено в API движка, в деле не проверялось); запасной путь — `WebSocketMultiplayerPeer` через `wss`.
- `SceneMultiplayer.set_auth_callback` / `send_auth` / `complete_auth` + `set_auth_timeout` вместо самодельного пароля в рукопожатии: токен или сессия, автоматический кик не прошедших проверку.
- `set_max_sync_packet_size` / `set_max_delta_packet_size` — ограничить размер пакетов.
- Проверка: клиент без токена отключается, с токеном — играет; пароль больше не идёт открытым текстом.

#### M6.4 Честность: серверная симуляция движения — **L**

Важно: сам по себе выделенный сервер читеров не останавливает — движение сейчас клиент-авторитетное, владелец сам пишет свою позицию.

- Клиент присылает ввод (или целевое состояние) с номером тика, сервер считает движение сам.
- Предсказание на клиенте и мягкая коррекция расхождений (сейчас есть только сглаживание чужой позиции).
- Валидация: скорость и телепорты, частота ударов, допустимые координаты.
- Проверка: клиент, который «телепортируется» в своей копии, у сервера и у остальных не смещается.

Решения, которые нужны до старта M6:

1. Кто и как запускает матч: автозапуск по числу игроков или один постоянный мир?
2. Хранить ли состояние мира между сессиями (сейчас всё в памяти `WorldSync`)?
3. Нужен ли сервер-браузер или достаточно прямого IP?
4. Хватит ли кика из консоли или админ-команды нужны в первой версии?

**Готово, когда (весь M6):** сервер поднимается одной командой на headless-машине, игроки подключаются и играют без «хозяина», уход любого игрока (включая последнего) не ломает мир, канал шифрован, а движение считает сервер. Порядок работ: M6.1 → M6.2 (рабочий сервер) → M6.3 → M6.4 (сервер для публики).

## 6. Оценка нагрузки на 20 игроков

Оценка (не замер): одно состояние игрока ≈ 30 байт (позиция + velocity + служебные поля), 20 игроков ≈ 600 байт на снапшот, при 20 Гц ≈ **12 КБ/с каждому клиенту** (≈ 96 кбит/с).

- Upload хоста: 19 клиентов × 12 КБ/с ≈ **230 КБ/с (≈ 1,9 Мбит/с)** — нормально для LAN, рискованно для домашнего интернета.
- Upload клиента: свое состояние ≈ 0,6 КБ/с — пренебрежимо.
- Вывод: без interest management 20 игроков на интернете — на грани; видимость по расстоянию (M5) обязательна, а не «полировка».
- **Фактический замер на 20 игроках (M5):** ~70 КБ/с отправки и ~74 КБ/с приёма у хоста, ~0,5 КБ/с на клиента за каждого видимого игрока. Оценка выше оказалась пессимистичной примерно втрое.
- Запас по надёжности: `create_server(port, max_clients, max_channels, in_bandwidth, out_bandwidth)` с явными лимитами.

## 8. Проверка (по конвенциям проекта)

- Гейт загрузки: `--headless --path . --quit` (ошибки компиляции и импорта — в stderr, успех — только баннер). Автотестов в проекте нет.
- Изоляция игровых событий по игроку (M0): `--headless --path . res://core/dev_checks/players_isolation_check.tscn` — грузит `map_1`, подселяет второго игрока, проверяет что чужие события не доходят, и печатает `M0 CHECK: OK` (код 1 при провале).
- Сетевой смоук после M1: хост-headless + N клиентов-headless, проверка лог-строк о подключении/отключении.
- Сетевой смоук (M1) — `res://core/dev_checks/network_smoke.tscn`, аргументы после `--`: `--autohost --name=Host --password=secret` (хост), `--autoconnect=127.0.0.1 --password=secret` (подключение), `--autoconnect=127.0.0.1 --password=wrong --expect-reject` (отказ по паролю), `--lan-search` (поиск игр в локальной сети). Успех — строки `SMOKE CLIENT CONNECTED`, `SMOKE CLIENT REJECTED: …`, `SMOKE LAN FOUND n`.
- Сетевой смоук (M2) — те же команды с `--start-game` у хоста и `--expect-game` у клиента: хост ждёт второго участника, начинает игру, затем сдвигает своего игрока на 400 px; клиент проверяет двух игроков, свой авторитет и камеру, затем ловит движение. Успех — `SMOKE CLIENT SEES MOTION`.
- Движение между двумя клиентами и поздний вход: хост `--solo-start --world` (игра уже идёт), затем клиент-бот `--bot --hold=N`, затем наблюдатель `--expect-game --watch-name=<ник бота>` (или `--watch-peer=<id>`) — обязан напечатать `SMOKE CLIENT SEES PEER <id> MOTION`. Без этого флага смоук следит только за хостом и репликацию клиент↔клиент через релей не проверяет — так и проскочил баг из §10.
- Проверки M3 в том же смоуке: клиент печатает `SMOKE CLIENT NAMEPLATE: <ник> <цвет>` (табличка чужого игрока видна, ник и цвет совпадают с ожидаемыми, своя табличка скрыта), хост печатает `SMOKE HOST COLOR: <цвет>` — значения обязаны совпасть.
- Проверки M4: хост `--start-game --world` ломает дерево и участвует в гонке за предмет, клиент `--expect-game --world` ждёт `SMOKE CLIENT SEES TREE GONE`, считает лут (`SMOKE CLIENT LOOT`) и печатает итог гонки (`SMOKE PICKUP CLIENT: won|lost`), успех — `SMOKE CLIENT WORLD OK`. Поздний вход: хост `--solo-start --world` ломает дерево до подключения, клиент подключается позже и обязан увидеть `SMOKE CLIENT SEES TREE GONE` и `SMOKE CLIENT LOOT: 3` из снапшота.
- Проверки M5 (масштаб): хост `--stress`, клиенты `--bot --hold=N`, итог каждого процесса пишется файлом (`--report=<имя>.txt` → `res://_dsh_reports/`), потому что stdout у процессов под `Start-Process` буферизуется. Успех — `SMOKE STRESS OK` у сервера и `SMOKE BOT DONE` у ботов; в прогоне 19 ботов + хост = 20 игроков держат сессию, у остальных счётчик игроков убывает при выходе ботов.
- Проверки экипировки и использования: клиент печатает `SMOKE EQUIP CLIENT: <узел> face_right=<bool> own_empty=<bool>` (видит чужое оружие и сторону, свои руки пусты) и `SMOKE USE CLIENT: <узел> playing=true` (видит чужую анимацию использования). Поздний вход проверяется тем же: хост `--solo-start --world` берёт оружие до подключения клиента, клиент обязан увидеть и предмет, и замах.
- Ручная проверка после каждой вехи: два обычных окна на localhost.

## 9. Открытые вопросы

Закрыто: 20 = «хост + 19 клиентов»; late join нужен; подключение и по IP, и через LAN-браузер; пароль — опциональная функция хоста; ники и цвета — вместе, в M3; чат — отдельная фича на будущее; одиночная игра — отдельный пункт меню; порт фиксированный 8910.

Осталось решить по ходу работ:

1. Разносить ли точки спавна, если 20 игроков мешают друг другу в одной точке — решение по результатам M5 (сейчас одна точка, 20 игроков проверены стрессом). Перенесено в M6.1.
2. Чат и прочие социальные фичи — вне рамок этого плана.
3. Всё, что касается выделенного сервера — шифрование канала, аутентификация, серверная симуляция движения — переехало в этап M6.
4. Включать ли радиус интереса `VISIBILITY_RADIUS = 1500` px (`INTEREST_RADIUS_ENABLED` в `player.gd`): он реализован, но выключен, потому что до фикса из §10 не действовал вообще, а включает его отдельный замер трафика. При включении далёкие игроки замирают и «прыгают» при подходе — это и есть задуманный interest management.

## 10. Почему репликация залипала у позднего входа (фикс после M5)

Симптом: игра уже идёт, подключается игрок — он видит остальных замершими, хотя его самого видят все и он двигается у себя нормально.

**Причина в движке, а не в обмене сообщениями.** `MultiplayerSynchronizer` адресует пакеты не путём узла, а коротким id из кэша путей (`SceneCacheInterface`): отправитель один раз шлёт получателю `SIMPLIFY_PATH`, и до подтверждения (`CONFIRM_PATH`) синхронизацию этому пиру не отправляет вовсе. Подтверждение приходит только если получатель нашёл узел по присланному пути — а он его не находит, пока не загрузил карту: `process_simplify_path` печатает `Node not found: "MainGame/Players/Player_<id>/NetTarget/MultiplayerSynchronizer"` и молча выходит. Повторной попытки у отправителя нет (в `confirmed_peers` уже лежит `false`), поэтому направление «от нас к новичку» умирает навсегда — и так у каждого пира, который начал синхронизацию, пока новичок был ещё в лобби (`peer_connected` приходит до рукопожатия и до загрузки карты). В обратную сторону репликация работает: свои узлы у новичка появляются раньше, чем он начинает слать.

**Почему не ловилось смоуком.** В сценарии M2 оба пира сидят в лобби до старта игры, узлы появляются у обоих уже после старта — хендшейк успевает. Поздний вход проверялся только по RPC (снапшот, экипировка, использование), а RPC потерю подтверждения переживают: иначе проверки экипировки у позднего входа падали бы.

**Фикс.**
1. `_apply_visibility` (`shared/actors/player/player.gd`) выключает видимость по умолчанию (`set_visibility_public(false)`) и включает её адресно только пирам, уже вошедшим в мир (`WorldSync.is_peer_in_world`): первый пакет уходит, когда узлы у получателя уже есть. Заодно это делает адресное вещание настоящим — до фикса `set_visibility_for` не сужал ничего, потому что публичная видимость оставалась включённой.
2. `WorldSync._check_snapshot_request` ждёт появления `MatchState.local_player`: заявка на снапшот — это и есть момент, когда остальные считают пира вошедшим, и она не должна уходить раньше, чем у него созданы узлы.
3. `EquippableItemHolder._on_peer_entered_world` больше не шлёт RPC самому себе (`rpc_id` на себя движок запрещает) — это сыпало ошибкой в лог у каждого новичка.

**Проверка:** хост `--solo-start --world`, затем бот-клиент `--bot --hold=26`, затем наблюдатель `--expect-game --watch-name=<ник бота>` — печатает `SMOKE CLIENT SEES PEER <id> MOTION`; со старым поведением падает с `движение игрока … не дошло`, а в stderr видно `Node not found … MultiplayerSynchronizer`.

**Осталось шумом** (на игру не влияет): широковещательные RPC `_remote_flip`/`_remote_equip` по-прежнему уходят пирам в лобби и оставляют в логе такие же `Node not found … EquippableItemHolder`; сами RPC доходят, но подтверждение кэша путей для таких пиров не сохраняется. Лечится тем же приёмом — адресной рассылкой только вошедшим в мир.
