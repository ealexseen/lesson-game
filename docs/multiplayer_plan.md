# План мультиплеера — LessonGame

Статус: **план согласован, реализация не начата**. Целевая версия движка — Godot 4.6 (GDScript).
Общение — по-русски, код и имена — по-английски (см. `AGENTS.md`).

## 1. Рамки

| Параметр | Решение |
|---|---|
| Режим | Кооп в общем мире, PvE |
| Топология | Listen-server: один из игроков — хост, у него авторитет по миру |
| Транспорт | ENet (UDP), релей трафика через сервер (`multiplayer.server_relay = true`) |
| Игроков | до **20** всего (хост + до 19 клиентов) |
| Подключение | ввод IP вручную **и** LAN-браузер (автопоиск хостов) |
| Порт | фиксированный — **8910**, в UI не настраивается |
| Пароль на вход | **опционально**: хост может задать пароль, пусто — вход свободный |
| Поздний вход (late join) | нужен: подключение к идущей игре с ресинком мира |
| Имена и цвета игроков | нужны: ник и цвет отображаются над персонажем |
| Чат | **не делаем** — отдельная фича на будущее (закладываем место, но не реализуем) |
| Точка спавна | пока одна общая на всех (пересмотреть при 20 игроках) |
| Одиночная игра | остаётся **отдельным пунктом** меню, отдельной ветки «мультиплеерной» логики для неё не делаем |
| Первая веха | техдемо: двое игроков бегают и видят друг друга |

## 2. Архитектура

```
                 ┌──────────────────────────────┐
                 │ Хост (listen-server)         │
                 │  авторитет по миру           │
                 │  мобы, лут, урон, двери,     │
                 │  спавн, состояние мира       │
                 └───────┬──────────────┬───────┘
                 ENet    │              │   ENet
        ┌────────────────┘              └────────────────┐
        │                                                 │
   ┌────▼─────┐                                      ┌────▼─────┐
   │ Клиент 1 │  … до 19 клиентов …                  │ Клиент N │
   │ свой ввод│  ввод и камера — только своё          │          │
   └──────────┘                                      └──────────┘
```

- **Сервер владеет:** спавном объектов, уроном, смертью мобов и объектов, подбором предметов, состоянием дверей, состоянием мира (что сломано/подобрано).
- **Клиент владеет:** своим вводом, своей камерой, своим курсором, предсказанием собственного движения.
- **Репликация движения:** `MultiplayerSynchronizer` на узле `Player` (позиция + velocity), интервал 1/20…1/30 с, с визуальным сглаживанием в `_process`.
- **Действия:** ручные `rpc`/`rpc_id` (стрельба, удар, подбор, дверь) — сначала на сервер, сервер рассылает результат.
- **Спавн объектов:** `MultiplayerSpawner` на уровне, спавнит только сервер (`spawn_function` сериализует путь сцены + `Transform2D`).
- **Пули:** авторитетны на сервере; на клиентах — визуал без физики и без размножения дочерних пуль.

### Проверенные API Godot 4.6

Наличие проверено движком (`--headless --script`, ClassDB): `ENetMultiplayerPeer.create_server/create_client/set_bind_ip`, `MultiplayerSpawner` (`spawn_function`, `spawn_path`, `spawn_limit`, `add_spawnable_scene`, `spawn`), `MultiplayerSynchronizer` (`replication_interval`, `replication_config`, `public_visibility`, `root_path`, `set_visibility_for`, `set_visibility_public`, `update_visibility`), `SceneMultiplayer` (`set_auth_callback`, `set_root_path`, `server_relay`, `allow_object_decoding`), `Node.set_multiplayer_authority/is_multiplayer_authority/rpc_config/rpc_id`, `SceneTree.get_multiplayer/set_multiplayer`, `ProjectSettings` — `physics/common/physics_interpolation`.

Важно: **`MultiplayerSynchronizer.add_property()` не существует** — список свойств задаётся через `replication_config` (`SceneReplicationConfig`), то есть в инспекторе. Список пиров берётся из `multiplayer.get_peers()` (метод `MultiplayerAPI`, не `SceneMultiplayer`).

## 3. Что блокирует в текущем коде

**№1 — глобальный `EventSystem` без адресата (главный блокер).** Сигналы `PLA_*`, `INV_*`, `EQU_*` (`core/global_events/event_system.gd`) слушают подписчики **всех** игроков:

- `shared/actors/player/managers/player_stats_manager/player_stats_manager.gd` — `PLA_change_energy` от одного игрока уменьшит энергию всем;
- `shared/gui/components/player_menu/managers/manager_inventory/manager_inventory.gd` — `INV_try_to_pickup_item` подберёт предмет каждому;
- `shared/actors/player/equippable_item_holder/equippable_item_holder.gd` — `EQU_equip_item` экипирует оружие всем;
- `shared/gui/components/player_stats/player_stats.gd` — HUD получает статы всех игроков подряд.

**№2 — ввод читается напрямую.** `shared/actors/player/player.gd` (`Input` в `_physics_process`, `_unhandled_key_input`), `shared/objects/door/door.gd` (`_input`, KEY_E/KEY_W), `shared/objects/items/components/items/base_item/pickuppable_item.gd` (`_input`, 'active'). Плюс проверки `body is Player`, реагирующие на **любого** игрока, а не на локального.

**№3 — камера и курсор.** `Camera2D` внутри `Player` (`shared/actors/player/player.tscn`) — активной должна быть только локальная. `CursorGame` и `get_global_mouse_position()` локальны по смыслу; на сервере направление выстрела берётся из RPC.

**№4 — мир управляется локально.** `HittableObjectTemplate.die()`, `AnimalTemplate.set_state(Dead)`, `ManagerSpawner.on_spawn_scene`, `EquippableWeaponeTemplate.check_hit()` выполняются в том процессе, где нажали.

**№5 — мелочи с последствиями.** Отладочный `Line2D` в `check_hit()` уедет в сетевую игру; `Bullet` — `RigidBody2D`, плодящий дочерние пули по коллизии (недетерминированная физика); статичный узел `Player` в `core/stages/levels/level_1.tscn`.

## 4. Проектные решения

1. **Авторитет.** Сервер решает всё, что меняет общий мир. Клиент присылает намерение («выстрелил в эту точку», «подобрать этот предмет»), сервер валидирует (дистанция, кулдаун, живость объекта) и рассылает результат.
2. **Развязка шины событий.** `EventSystem` остаётся для UI/системных сигналов (`UI_*`, `BUL_*`, `SPA_spawn_scene`); игровые `PLA_*` / `INV_*` / `EQU_*` получают первым аргументом владельца (`player: Player` или `peer_id`), подписчики фильтруют `if owner != local_player: return`. Альтернатива — локальная шина-ребёнок `Player` — чище, но инвазивнее; начинаем с первого варианта, потому что он диффится постепенно и не ломает одиночную игру.
3. **Репликация движения** — `MultiplayerSynchronizer`; при необходимости позже снапшот-буфер с интерполяцией и `physics/common/physics_interpolation`.
4. **Поздний вход** — сервер по `peer_connected` присылает снапшот мира: список уже уничтоженных объектов и подобранных предметов. Источник истины — `MatchState`/`WorldState` (словарь `node_path → состояние`), а не сами узлы сцены.
5. **LAN-поиск** — `PacketPeerUDP` с `set_broadcast_enabled(true)`: хост раз в секунду шлёт бродкаст-бекон `{name, port, players, max, has_password}` на фиксированный порт, клиенты слушают и собирают список; ручной ввод IP остаётся как запасной путь (и на случай, когда бродкаст режется фаерволом).
6. **Имена и цвета игроков** — часть `MatchState`: `peer_id → {name, color}`; ник и цвет над персонажем — в составе `player.tscn`.
7. **Одиночная игра** — не отдельная кодовая ветка: тот же `PlayerSpawner` создаёт одного локального игрока без сети (`multiplayer.multiplayer_peer == null`).
8. **Порт** — фиксированный `8910`: `const DEFAULT_PORT := 8910` в `NetworkManager`, поля порта в UI нет. Если порт занят — понятная ошибка при попытке хостить, а не молчаливый отказ.
9. **Пароль (опциональная функция).** Хост может задать пароль в лобби; пустое поле — вход свободный. Реализация — рукопожатие после установления соединения: клиент сразу после `connected_to_server` отправляет `rpc_id(1, ...)` с паролем, сервер сравнивает и при несовпадении отключает пира (`multiplayer.multiplayer_peer.disconnect_peer(id)`) с сообщением. **До успешной проверки игрок не спавнится и не переводится на карту** — иначе пароль обходится сторонним клиентом. Пароль защищает от случайных подключений, но не от перехвата: канал не шифруем, шифрование (DTLS в ENet) — отдельная задача с проверкой API.

## 5. Этапы

Размеры: S — мало, M — средне, L — много.

### M0. Развязка игроков от глобальной шины (без сети) — **L**

- Автолоад `MatchState`: `local_player`, `players`, `is_host`, `max_players = 20`.
- Игровые сигналы получают адресата; все подписчики фильтруют по владельцу.
- `body is Player` → `body == MatchState.local_player` в `pickuppable_item.gd`, `door.gd`.
- `Player`: физика и ввод — только для локального игрока; камера `enabled` только у локального.
- HUD привязывается к локальному игроку.

**Готово, когда:** одиночная игра играется ровно как раньше, `--headless --path . --quit` без ошибок.

### M1. Транспорт, лобби, LAN-поиск, пароль — **M**

- `NetworkManager`: `const DEFAULT_PORT := 8910`, `host()`, `join(ip)`, `disconnect()`, сигналы `peer_joined/peer_left/connection_failed/host_left/join_rejected(reason)`; `ENetMultiplayerPeer.create_server(DEFAULT_PORT, 19)`, корректные тексты ошибок (в том числе «порт занят»).
- Рукопожатие с паролем: если хост задал пароль, игрок до проверки не спавнится и не переводится на карту; при несовпадении — отключение с сообщением (см. §4 п.9).
- Экран лобби `navigation_multiplayer` по образцу `navigation_base`: поле IP, поле пароля (опционально), «Создать игру» / «Присоединиться», список LAN-хостов, список игроков, статус; `ESC` → `EventSystem.UI_last` (как в `settings_root.gd`).
- `UIConfig.Keys.MenuMultiplayer = 5` + путь в `ui_config.gd`; кнопка «Мультиплеер» → `UI_replace`.
- `LanDiscovery` + вывод найденных хостов в лобби (хост с паролем в списке помечается, вход — по вводу пароля).

**Готово, когда:** два запуска игры соединяются и по IP, и через LAN-браузер; список игроков обновляется; свободный хост пускает без пароля, хост с паролем пускает только с верным паролем; отказ соединения показывает внятное сообщение, а не зависание.

### M2. Техдемо: игроки в мире (первая веха) — **M**

- Хост и клиенты синхронно переходят на `map_1.tscn`; статичный `Player` из `level_1.tscn` убирается, появляется нода `Players` + `PlayerSpawner`.
- Сервер по `peer_connected` инстансит `player.tscn`, вызывает `set_multiplayer_authority(peer_id)`, ставит на общую точку спавна.
- `MultiplayerSynchronizer` на позицию и velocity; сглаживание у наблюдателей.
- Чужой ввод, чужая камера и чужой курсор отключены; менеджеры чужого игрока не крутят логику.
- Dev-флаги для быстрого теста: `--autohost`, `--autoconnect=<ip>`, `--name=<ник>` (через `OS.get_cmdline_user_args()`, то есть после `--`; порт берётся из `NetworkManager.DEFAULT_PORT`).

**Готово, когда:** два окна на localhost видят оба тела, движение плавное, ничего не дёргается и не двоится; headless-прогон «хост + клиент» пишет в лог установленное соединение (это становится регрессионным гейтом вместо отсутствующих тестов).

### M3. Имена, цвета и список игроков — **S**

- Ник и цвет над персонажем (`nameplate`), у локального игрока скрыт; цвет берётся из `MatchState` и одинаков у всех.
- Список игроков в лобби/игровом меню: ник, цвет, пинг, пометка хоста.
- Лимит 20: отказ в подключении сверх лимита с понятным сообщением.

**Готово, когда:** ники и цвета видны и совпадают у всех, цвета различимы, 21-й игрок получает отказ и не ломает сессию.

### M4. Авторитет мира и поздний вход — **L**

- Стрельба и удары: raycast и урон выполняет сервер, направление приходит в RPC; отладочный `Line2D` — под флагом.
- Смерть дерева/камня/моба → спавн лута и `queue_free` только на сервере, рассылка всем.
- Подбор предмета: RPC на сервер, сервер решает «кто первый», убирает объект у всех, кладёт в инвентарь конкретному игроку.
- Двери: `_is_open` — сервер, телепорт — только для своего игрока.
- Инвентарь/хотбар/статы: владелец → сервер, синхронизация владельцу.
- `WorldState` + снапшот для late join.

**Готово, когда:** двое рубят одно дерево — лут достаётся одному; моб умирает один раз; предмет не дублируется; подключившийся позже видит уже сломанное дерево сломанным.

### M5. Масштаб до 20 игроков и устойчивость — **L**

- Interest management: `MultiplayerSynchronizer.set_visibility_for()` + `update_visibility()` по расстоянию — в мире шириной ~12 000 px это главный рычаг по трафику.
- Троттлинг: `replication_interval` 1/20, отказ от синхронизации лишних свойств, `MultiplayerSpawner.spawn_limit`.
- Выход игрока и выход хоста: очистка узлов, возврат в меню с сообщением; повторный вход.
- Стресс-тест: 20 headless-клиентов, замер трафика и CPU хоста, профилирование.
- Проверка на искусственном лаге.

**Готово, когда:** 20 headless-клиентов держат сессию стабильно, трафик хоста укладывается в бюджет (см. §6), отключение любого участника не ломает игру.

## 6. Оценка нагрузки на 20 игроков

Оценка (не замер): одно состояние игрока ≈ 30 байт (позиция + velocity + служебные поля), 20 игроков ≈ 600 байт на снапшот, при 20 Гц ≈ **12 КБ/с каждому клиенту** (≈ 96 кбит/с).

- Upload хоста: 19 клиентов × 12 КБ/с ≈ **230 КБ/с (≈ 1,9 Мбит/с)** — нормально для LAN, рискованно для домашнего интернета.
- Upload клиента: свое состояние ≈ 0,6 КБ/с — пренебрежимо.
- Вывод: без interest management 20 игроков на интернете — на грани; видимость по расстоянию (M5) обязательна, а не «полировка».
- Запас по надёжности: `create_server(port, max_clients, max_channels, in_bandwidth, out_bandwidth)` с явными лимитами.

## 7. Риски

| Риск | Митигация |
|---|---|
| Рефакторинг шины событий задевает почти все игровые скрипты | Отдельный M0 до всякой сети, проверка одиночной игры после каждого блока |
| Физика `RigidBody2D`-пуль недетерминирована, дочерние пули размножаются на клиентах | Клиентские пули — визуал без физики, попадания считает сервер |
| Двойной спавн из-за `ManagerSpawner` + `SPA_spawn_scene` | Единая точка: спавнит только сервер, остальные только слушают |
| Рассинхрон при смене сцены у пиров | Переход на `map_1` инициирует хост, клиенты грузят ту же сцену |
| Хост ушёл — сессия кончилась (цена listen-server) | Явное сообщение всем клиентам и возврат в меню; выделенный сервер — возможное продолжение |
| Одна точка спавна на 20 игроков — куча в одном месте | Временно приемлемо; в M5 разнести точки спавна, если мешает |
| Пароль идёт по незашифрованному каналу | Пароль закрывает от случайных подключений, но не от перехвата; шифрование (DTLS в ENet) — отдельная задача |
| Правки `map_1.tscn`/`level_1.tscn` ломают `unique_id`/`parent_id_path` | Только добавление узлов, проверка загрузкой после каждого шага |
| Тестировать вручную тяжело | Dev-флаги автохост/автоподключение + headless-прогон как гейт |

## 8. Проверка (по конвенциям проекта)

- Гейт загрузки: `--headless --path . --quit` (ошибки компиляции и импорта — в stderr, успех — только баннер). Автотестов в проекте нет.
- Сетевой смоук после M1: хост-headless + N клиентов-headless, проверка лог-строк о подключении/отключении.
- Ручная проверка после каждой вехи: два обычных окна на localhost.
- Масштаб (M5): 20 headless-клиентов + замер трафика и CPU хоста.

## 9. Открытые вопросы

Закрыто: 20 = «хост + 19 клиентов»; late join нужен; подключение и по IP, и через LAN-браузер; пароль — опциональная функция хоста; ники и цвета — вместе, в M3; чат — отдельная фича на будущее; одиночная игра — отдельный пункт меню; порт фиксированный 8910.

Осталось решить по ходу работ:

1. Разносить ли точки спавна, если 20 игроков мешают друг другу в одной точке — решение по результатам M5.
2. Нужно ли шифрование канала (DTLS) — сейчас не делаем; перед реализацией проверить API ENet в 4.6.
3. Нужен ли выделенный headless-сервер как продолжение listen-server — отдельная задача после M5.
4. Чат и прочие социальные фичи — вне рамок этого плана.
